# Архитектурные правила проекта

Этот файл обязателен для всех агентов и разработчиков, которые изменяют репозиторий. Правила распространяются на весь проект.

## Контекст приложения

- Это полноценное SPA, а не микрофронтенд.
- Точка входа приложения — `src/main.tsx`.
- Основной стек: Vite, React, TypeScript и pnpm.
- Стилизация: SCSS Modules; глобальные reset, тема и фон находятся в `src/app/styles`.
- Формы реализуются через React Hook Form.
- Для стандартных иконок используется `react-icons`.
- React Router, TanStack React Query, ky и Zustand установлены для будущих задач. Не добавлять их в runtime-код и не создавать конфигурационные обёртки или store-файлы без реального сценария использования.

## Режим разработки frontend

- Во время разработки frontend запускается локально через pnpm/Vite; Docker-контейнер frontend для этого не используется.
- После изменений frontend-кода не пересобирать, не перезапускать и не обновлять frontend-контейнер в Docker Compose.
- Для локальной проверки использовать команды из директории `frontend`: `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:e2e`, `pnpm build` и при необходимости локальный dev-сервер.
- Работать с frontend-контейнером допускается только по явному запросу пользователя, например для проверки полной Docker-сборки или развёртывания.
- Это ограничение не запрещает использовать Docker для backend, PostgreSQL и специальных изолированных тестовых сервисов.

## Использование Superpowers

- Навыки `superpowers:*` во всех режимах, включая `Plan mode` и `Default mode`, используются только по явному требованию пользователя.
- Без явного требования пользователя навыки `superpowers:*` не вызывать и не применять.

## Слои и направление зависимостей

Исходный код следует упрощённому Feature-Sliced подходу:

```text
app → pages → widgets → entities → shared
```

Слой слева может импортировать слои справа. Обратные зависимости запрещены.

| Источник | Допустимые зависимости |
| --- | --- |
| `app` | `pages`, `widgets`, `entities`, `shared` |
| `pages` | `widgets`, `entities`, `shared` |
| `widgets` | `entities`, `shared` |
| `entities` | связанные `entities`, `shared` |
| `shared` | только `shared` |

Дополнительные правила:

1. Слои `pages` и `widgets` не импортируют соседние слайсы своего слоя.
2. Связи между сущностями допустимы, только если они отражают предметную модель, направлены в одну сторону и не создают циклы.
3. `shared` не содержит бизнес-логики и ничего не знает о страницах, виджетах или сущностях.
4. Слой `features` в проекте не используется и не должен создаваться.
5. `assets`, `declarations`, `test` и корневая директория `e2e` являются техническими каталогами, а не архитектурными слоями.

## Правило ближайшего владельца

Новый код размещается как можно ближе к месту, которому он принадлежит. Поднимать код на более общий уровень следует только при реальном переиспользовании или появлении самостоятельной ответственности.

- Сценарий одной страницы остаётся внутри слайса этой страницы.
- Составной UI-блок с собственным поведением, используемый несколькими страницами, относится к `widgets`.
- Бизнес-типы, расчёты, преобразования и правила устойчивого предметного понятия относятся к `entities/{name}`.
- Универсальный UI или технический код без бизнес-смысла относится к `shared`.
- Не переносить локальный компонент в `widgets` или `shared` только ради сокращения пути импорта.

Внутри владельца допустимы локальные `components`, `hooks`, `utils`, `types`, `constants`, `__tests__` и SCSS Modules. Дочерний код хранится рядом с родителем.

## Декомпозиция компонентов

Компоненты декомпозируются по самостоятельным смысловым и поведенческим блокам. Родительский компонент отвечает за композицию и передачу данных, а не содержит полную реализацию всех вложенных частей интерфейса.

- Самостоятельный блок интерфейса с собственной разметкой, поведением или состоянием выносится в дочерний компонент.
- Состояние, обработчики, константы, типы и утилиты, используемые только дочерним компонентом, переносятся к этому компоненту.
- Код не поднимается в общий каталог владельца, если он относится только к одному дочернему компоненту.
- Дочерние компоненты располагаются в локальной папке `components`; у этой папки должен быть `index.ts`.
- Вложенный компонент оформляется отдельной директорией с одноимённым файлом компонента и `index.ts`.
- Родитель импортирует дочерние компоненты через локальный `components/index.ts`.
- Компонент не дробится механически: отдельный файл создаётся для смыслового блока, самостоятельного поведения или заметного объёма разметки, а не для одиночного тривиального элемента.

Пример структуры:

```text
BondDetails/
├── components/
│   ├── IssueInformation/
│   │   ├── IssueInformation.tsx
│   │   ├── utils.ts
│   │   ├── __tests__/
│   │   └── index.ts
│   ├── NextCoupon/
│   │   ├── NextCoupon.tsx
│   │   └── index.ts
│   └── index.ts
├── BondDetails.tsx
├── BondDetails.module.scss
└── index.ts
```

Утилиты размещаются у ближайшего компонента-владельца по следующим правилам:

- Если утилитарная функция одна, создаётся `utils.ts` на уровне компонента. Её тесты размещаются в соседней папке `__tests__` на том же уровне.
- Если утилитарных функций несколько, создаётся папка `utils`, каждая функция помещается в отдельный одноимённый файл и экспортируется через `utils/index.ts`.
- Тесты нескольких утилит размещаются в `utils/__tests__`.
- Утилиты и их тесты не экспортируются через публичный API компонента, если они не нужны внешнему клиенту.
- При переносе смыслового блока существующие локальные утилиты, константы, типы и тесты также переносятся к новому владельцу.

## Ответственность слоёв

### `app`

Собирает приложение и содержит только глобальную композицию:

- глобальные провайдеры;
- подключение страниц и будущего роутера;
- глобальные стили и тему;
- общую инициализацию внешних библиотек;
- глобальные обработчики ошибок.

Не размещать здесь бизнес-сущности или реализацию отдельных страниц.

### `pages`

Первый уровень состоит из независимых слайсов страниц. Простая страница хранит основной компонент в корне слайса:

```text
pages/BondCalculatorPage/
├── components/
├── __tests__/
├── BondCalculatorPage.tsx
├── BondCalculatorPage.module.scss
├── types.ts
└── index.ts
```

Если один раздел позднее объединит несколько маршрутов, допускается внутренняя группировка `screens`. `screen` не является отдельным слоем и не импортируется другой страницей.

Текущая форма калькулятора, панель результата и меню пресетов принадлежат только `BondCalculatorPage`, поэтому остаются её локальными компонентами.

### `widgets`

Используется для крупных самостоятельных UI-блоков, которые решают законченную часть сценария, объединяют компоненты или сущности и реально переиспользуются страницами либо глобальной компоновкой.

Widget может импортировать только `entities` и `shared`. Он не может импортировать другой widget, `pages` или `app`.

### `entities`

Содержит общий предметный API приложения: модели, бизнес-правила, чистые расчёты, форматирование предметных значений, работу с данными и связанное состояние.

Слайс `entities/bondCalculation` является владельцем типов и логики расчёта облигаций, а также совместимости сохранённых расчётов. Не дублировать эту логику в странице или `shared`.

Внутри сущности допустимы `types.ts`, `api.ts`/`api`, `constants.ts`, `store.ts`/`store`, `hooks`, `utils` и `ui`. Создавать только действительно нужные сегменты.

### `shared`

Содержит переиспользуемый технический код без бизнес-привязки:

- `shared/ui` — универсальные компоненты;
- `shared/lib` — чистые технические функции;
- будущий `shared/api` — базовый HTTP-клиент и транспортная инфраструктура;
- будущие `shared/hooks`, `shared/types`, `shared/constants` — только технические абстракции.

Компонент `shared/ui` получает всё необходимое через props, не выполняет доменные запросы, не читает состояние сущностей и не зависит от конкретных маршрутов.

Кастомные React-иконки хранятся по схеме:

```text
shared/ui/icons/{IconName}/
├── {IconName}.tsx
├── {IconName}.module.scss  # если нужны стили
└── index.ts
```

Папка `shared/ui/icons/index.ts` собирает публичный API кастомных иконок, а клиенты импортируют их только через `#shared/ui`.

## Публичные API и импорты

Для межслойных импортов использовать настроенные алиасы:

```text
#app
#pages/*
#widgets/*
#entities/*
#shared/*
#assets/*
```

Импорт должен проходить через публичный `index.ts` слайса или сегмента.

```ts
// Допустимо
import type { BondCalculationResult } from '#entities/bondCalculation';
import { Button, BarChartIcon } from '#shared/ui';

// Недопустимо: обход публичного API
import type { BondCalculationResult } from '#entities/bondCalculation/types';
import { Button } from '#shared/ui/Button/Button';
```

Внутри одного слайса или модуля использовать относительные импорты. Не импортировать собственный слайс через его публичный alias: это скрывает локальную связь и может создать цикл через barrel-файл.

Обязательные публичные точки входа:

- каждый слайс `pages`, `widgets` и `entities` имеет `index.ts`;
- локальная папка `components` внутри страницы, виджета или составного компонента имеет `index.ts`;
- вложенный модуль, используемый за пределами своей директории, имеет локальный `index.ts`;
- используемые через alias сегменты `shared` имеют `index.ts`.

Публичный API экспортирует только то, что требуется клиентам. Не раскрывать локальные хуки, внутреннее состояние и детали реализации без необходимости.

## Состояние и внешние библиотеки

Состояние размещается у ближайшего владельца:

| Вид состояния | Размещение |
| --- | --- |
| состояние компонента | рядом с компонентом |
| состояние формы | React Hook Form внутри владельца формы |
| состояние одной страницы | соответствующий слайс `pages` |
| состояние самостоятельного виджета | соответствующий слайс `widgets` |
| общее состояние бизнес-сущности | `entities/{name}/store.ts` или `store/` |
| подключение глобального provider | `app/providers` |

Будущая сетевая инфраструктура размещается так:

- базовый клиент ky и техническая обработка ошибок — `shared/api`;
- запросы, DTO и адаптеры конкретной сущности — `entities/{name}/api`;
- композиция React Query только для одной страницы — локальный хук страницы;
- переиспользуемая доменная композиция запросов — хук сущности.

## Стили и UI

- Компонентные стили оформляются через `*.module.scss` и располагаются рядом с владельцем.
- Глобальные CSS-переменные, reset, фон и правила темы остаются в `app/styles`.
- Не переносить бизнес-тексты или доменные варианты поведения в `shared/ui`.
- Использовать `react-icons` для доступных стандартных иконок; собственные иконки размещать в `shared/ui/icons`.
- При визуальных изменениях сохранять обе темы, адаптивные состояния и `prefers-reduced-motion`.

## Тесты

- Unit- и component-тесты размещаются в `__tests__` рядом с владельцем и используют суффикс `.spec.ts`/`.spec.tsx`.
- Тесты не входят в публичный API модуля.
- End-to-end тесты находятся в корневом `e2e` и проверяют приложение через публичный UI.
- Общие E2E fixtures и helpers остаются внутри `e2e`, а не переносятся в `shared`.

Перед завершением значимых изменений выполнить:

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm test:e2e
pnpm build
```

Объём проверки можно уменьшить только для очевидного локального изменения, не затрагивающего поведение, типы или сборку.

## Контрольный список перед добавлением нового модуля

1. Определён ближайший владелец кода.
2. Не создаётся слой `features` или общий корневой `store`.
3. Направление зависимости соответствует `app → pages → widgets → entities → shared`.
4. Межслойный импорт проходит через alias и публичный `index.ts`.
5. Внутри владельца используются относительные импорты.
6. Бизнес-логика не попала в `shared`.
7. Новый публичный экспорт действительно нужен внешнему клиенту модуля.
8. Добавлены или обновлены соразмерные риску тесты.
9. Составной компонент разделён на самостоятельные смысловые блоки, а локальный код находится у ближайшего компонента-владельца.
10. Для локальных папок `components`, `utils` и вложенных модулей добавлены необходимые `index.ts`.
